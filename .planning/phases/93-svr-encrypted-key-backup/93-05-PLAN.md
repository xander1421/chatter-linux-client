**Constraining decisions:**
- PIN is already required at registration (validated as 6 digits in auth_service)
- PIN is already required at login (derived into svr_public_key)
- Registration: backup happens AFTER successful registration (identity keys already generated)
- Login: restore happens AFTER successful auth, BEFORE normal app startup, IF local identity keys are missing
- svr_secret is derived from PIN+username, used transiently, never stored
- If backup restore fails (wrong PIN, no backup, rate limited), log in anyway without keys — user can try again or re-register

**Key insight:**
- `SvrKeypair::secret_bytes()` is currently UNUSED — this plan is where it gets called for the first time
- The svr_secret used for backup is `derive_svr_secret(pin, username)`, NOT `SvrKeypair::secret_bytes()` (which is the x25519 clamped version). Use the raw Argon2id output directly as AES key.

  <action>
In the `login` method, AFTER authentication succeeds, detect whether this is a new device (no local identity keys) and attempt backup restore:

1. After login succeeds (auth_client.login returns OK), check if local identity keys exist:
   - `self.key_store.get_identity_key_pair()` or equivalent — check what method exists
   - If identity keys exist locally → skip restore (existing device, keys are fine)
   - If identity keys are missing → this is a new device, attempt restore

2. If new device:
   a. Derive svr_secret: `crate::crypto::svr::derive_svr_secret(pin, username)?`
   b. Call `svr_backup_service.fetch_and_restore_backup(&svr_secret).await`
   c. On success, hydrate local stores:
      - Store identity_keypair via IdentityKeyManager or KeyStore
      - Store profile_key via settings_repo.set_bytes(keys::PROFILE_KEY, &payload.profile_key)
   d. Zeroize svr_secret and payload after hydration
   e. On failure: log warning, continue login. User has auth but no E2E keys — they'll need to re-register or try PIN again.

3. Add to LoginResult (or return type) a flag indicating whether keys were restored, so the UI can inform the user:
   - `keys_restored: bool` — true if backup was fetched and decrypted
   - `keys_missing: bool` — true if new device and restore failed

**Error handling:** Restore failure is NOT a login failure. Map errors:
- `SvrBackupError::RateLimited` → log "Too many attempts, try later", set keys_missing
- `SvrBackupError::BackupNotFound` → log "No backup found", set keys_missing
- `SvrBackupError::Crypto(_)` → log "Wrong PIN or corrupted backup", set keys_missing
- `SvrBackupError::Network(_)` → log "Network error during restore", set keys_missing

The UI layer can later show appropriate messaging based on these flags.
